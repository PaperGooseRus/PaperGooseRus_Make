# PaperGooseRus_Make

Интерактивная система сборки проектов C/C++ на базе GCC. Язык реализации: **C++17**. Основная логика находится в `.hpp`; главное меню работает в цикле до команды выхода.

Текущая версия: **Stage 6 — протоколирование и контроль процесса сборки**. Функциональность Stage 1–5 сохранена.

## Stage 6. Полный протокол процесса сборки

Цель Stage 6 — **восстановить цепочку получения результата**: почему GCC был запущен,
какие именно аргументы получил, что прочитал, что создал, сколько времени потратил
и что сделала инкрементальная сборка.

### Спецификация и требования

- **Четыре функции GCC сохранены раздельными**: `preprocessing()`, `compilation()`,
  `assembly()` и `linking()`. Добавлены два самостоятельных header-only модуля:
  `core/plan/build_plan.hpp` и `core/report/build_report.hpp`.
- `gcc_t::preview(project)` читает состояние зависимостей, кэша и выходных файлов,
  но **не создаёт файлов, не вызывает GCC и не переписывает кэш**. При первом запуске
  операции обозначаются `PLAN`, после успешной сборки неизменённые операции — `SKIP`.
- В реальной сборке фиксируются `PREPROCESSING`, `COMPILATION`, `ASSEMBLY`, `LINKING`
  и вызовы Binutils (`BINARY`) с результатом `EXECUTED`, `SKIPPED` или `FAILED`.
  Причины: `FIRST_BUILD`, `COMMAND_CHANGED`, `INPUTS_CHANGED`,
  `OUTPUT_MISSING_OR_STALE`, `ANALYSIS_MISSING`, `UP_TO_DATE`,
  `PREPROCESSING_UPDATED`, `COMPILATION_UPDATED`, `OBJECT_UPDATED` и другие.
- Точная запущенная команда, разобранные аргументы, действительный рабочий каталог
  процесса, UTC-время начала, длительность в миллисекундах, код завершения,
  входные и выходные отпечатки сохраняются в `reports/build-report.json`.
  Для пропущенных крупных промежуточных файлов вместо повторного чтения хеша
  ставится `VALIDATED_BY_BUILD_CACHE`.
- `build-manifest.json` содержит контрольные суммы исходников и зависимостей `.d`,
  идентификаторы GCC/G++ и инструментов Binutils (версии, пути, отпечатки),
  минимальный набор переменных среды (`PATH`, `LANG`, `LC_ALL`, `SOURCE_DATE_EPOCH`),
  конечные объекты и исполняемый файл.
- `compile_commands.json` формируется для clangd и других инструментов: записи
  относятся к **оригинальным `.c/.cpp`**, а не к `.i/.ii`. Это эквивалентные
  source-level вызовы для инструментов IDE; **реальные** последовательные команды
  PGR Make записаны в `build-report.json`.
- Если GCC завершился с ошибкой, отчёт всё равно создаётся с результатом `FAILED`
  и ненулевым `exit_code`. Ошибка записи отчёта сама считается ошибкой сборки.

### Работа с интерфейсами

В циклическом CLI есть **14. Preview build plan (dry run)** или команда `plan`.
Для запуска CLI при компиляции GUI используйте `pgr_gui.exe --cli .`.
В интерфейсе libadwaita добавлены кнопка **«План сборки»** и нижняя вкладка
**«План»**, в которой отображаются решения `PLAN/SKIP` и аргументы GCC.
Нижняя панель «Вывод сборки» по-прежнему показывает реальные сообщения.

### Четыре проверяемых шага Stage 6

1. **Простая сборка:** один `main.c`, четыре записи `EXECUTED` и работающий `.exe`.
2. **Повторная сборка:** четыре записи `SKIPPED`, ноль запусков GCC.
3. **Изменённая зависимость/флаг:** в отчёте есть причины `INPUTS_CHANGED` и
   `COMMAND_CHANGED`, а перелинковка помечена `OBJECT_UPDATED`.
4. **Ошибки и preview:** неудачная компиляция сохраняет `FAILED`; dry-run не меняет
   каталог сборки и созданные JSON-файлы.

```bash
python tests/test_build_trace.py
python tests/test_incremental.py
python tests/test_analysis.py
python tests/test_embedded.py
python tests/test_regressions.py
python tests/test_gtk_ui.py
```

**Ограничения Stage 6:** план показывает ожидаемую работу на основании текущего
кэша и не предсказывает содержимое ещё не созданных промежуточных файлов.
Фактические версии `as` и `ld` берутся из доступного окружения; GCC при сложных
настройках может выбрать другие внутренние инструменты. Режим `gcc -###` не
запускается автоматически. Тайм-ауты/отмена процессов, параллельная компиляция и
строгая воспроизводимость относятся к следующим этапам. Встроенный GTK4
проверен синтаксически с тестовыми заголовками: реальная сборка и запуск
требуют установленного MSYS2 UCRT64 SDK на Windows.

## Графический интерфейс Adwaita (GUI Workbench)

Графический интерфейс реализован **только в `gui/gtk_app.hpp`**, поверх существующих
`gcc_t`, `project_t`, `config_t`, `loger_t`, `binary_t`. Новые зависимости:
GTK4, **libadwaita 1.4+** и **GtkSourceView 5**. Пользовательский CSS не применяется;
оформление обеспечивает libadwaita и системная тема.

**Рабочая область:**
- **Слева** проводник исходных файлов с фильтром, просмотром исходников и заголовков.
  Проводник показывает файлы проекта, а выбор файлов для сборки сохраняется на
  отдельной вкладке **«Исходники»**. Поиск работает по относительному пути.
- **В центре** вкладки обзора проекта, выбора файлов, GCC, исследования GCC,
  Embedded, монитора сборки и просмотра исходного кода через GtkSourceView.
- **Внизу** постоянно доступный и изменяемый по высоте вывод GCC и вкладка ошибок.
  Журнал читается добавлением новых байтов; объём текста ограничен.
- **В шапке** выбор каталога проекта, запуск сборки, сохранение профиля, индикатор
  активности. Для работы с целями используется прежнее текстовое поле «Профиль / цель».
- **Окно настроек** пока заменяет вкладка «GCC», чтобы сохранить все возможности
  существующего интерфейса без дублирования конфигураций.

Монитор показывает четыре этапа GCC и реальные сообщения из журнала.
Индикатор активности **не является процентом готовности**: до появления плана сборки
невозможно точно вычислить процент выполнения.
Нижняя вкладка **«Вывод сборки» не является интерактивным терминалом**.
Кнопка «Windows Terminal» запускает отдельную оболочку в каталоге проекта, если
`wt.exe` доступен в `PATH`. На Linux выполняется попытка открыть `gnome-terminal`.
Встроенная оболочка с ConPTY пока не реализована.

### Установка и сборка в MSYS2 UCRT64


GTK4»**, которое получает `--cflags` и `--libs` для всех трёх библиотек через
`pkg-config` и выбирает цель `GTK4`.

**Тестирование:** консольная сборка и тесты Stage 2–5 проверены на Linux/GCC.
В доступной среде отсутствуют GTK4/libadwaita/GtkSourceView SDK, поэтому реальную
компиляцию нового GUI и запуск на Windows/MSYS2 необходимо проверить на целевом ПК.

## Запуск GTK4 на Windows/MSYS2: локальный режим GApplication

В `gui/gtk_app.hpp` используется `G_APPLICATION_NON_UNIQUE`: графический интерфейс
запускается в текущем процессе, без согласования единственного экземпляра по
идентификатору `org.pgr.make`. Это устраняет зависимость регистрации приложения
от доступности session bus, которая в некоторых окружениях Windows может
приводить к `Failed to register: Истекло время ожидания`.

```bat
build_gui.cmd
build\pgr_gui.exe .
```

Примечание: программа может открывать несколько независимых окон при повторном
запуске. Тестирование GTK4 в Windows/MSYS2 выполняется на целевой машине;
в среде подготовки пакета отсутствует установленный GTK4 SDK.

## Этап 5. Исправления надёжности и архитектуры

В Stage 5 внесены исправления в текущий проект без перехода на CMake или внешнюю систему сборки. Все добавленные модули остаются **header-only**. Этапы `preprocessing()`, `compilation()`, `assembly()` и `linking()` **сохранены раздельными**.

### Основные изменения

| Недостаток Stage 4 | Исправление Stage 5 |
|---|---|
| Командная оболочка для запуска GCC/Binutils | `core/process/process.hpp`: прямой запуск процессов и перехват stdout/stderr. На POSIX `fork/execvp`; на Windows `CreateProcessW`. |
| Библиотека `.a` изменена, но линковка пропущена | `core/cache/cache.hpp`: хэш FNV-1a содержимого `.a`/`.so`/`.dll.a`/`.lib` из объявленных каталогов `-L`, всех `.o`, зависимостей `.d` и файлов linker script с `INCLUDE`. |
| Подмена времени изменения исходника | Сравнение контрольных сумм файлов `.c/.cpp`, `.h/.hpp` и `.S` по `cache/*.inputs`. |
| Изменение GCC/binutils без изменения команды | Учитываются фактические файлы GCC-драйверов и нужных Binutils, найденные через `PATH`. |
| Два `main()` в одном проекте | Меню **13** выбирает исходники для текущей цели; пустой список означает автосканирование. |
| Нет независимых целей сборки | Меню **12** переключает профили/цели. Каталоги кэша и результатов изолируются (`Project__Debug`, `Project__Release`). |
| Настройки терялись при выходе | Профили `.pgr/<target>.cfg`, сохранение командой **12 → 2**, загрузка при выборе цели и `default.cfg` при старте. |
| Нет ассемблерных единиц трансляции | `.s` и `.S` сканируются и компилируются; заголовки `.S` отслеживаются через `.d`. |
| CLI сообщает об ошибке, но процесс возвращает `0` | `cli_t::run()` возвращает код **последней попытки сборки**, даже после интерактивного выхода `0`. |
| Нет проверки размещения секций | `binary/memory.txt` из `objdump -h`, адресов VMA/LMA и заданных Flash/RAM; явное пересечение границы региона считается ошибкой. |
| Слишком много обязанностей у `gcc_t` | Кэш, процесс и профили выделены в отдельные классы `cache_t`, `process_t`, `config_t`. |

### Работа с целями и исходниками

1. **12 → 1**: выберите профиль `Debug`, `Release` или `Embedded`; отсутствие файла профиля означает новую конфигурацию.
2. **13**: вводите относительные пути конкретных исходных файлов (`main.cpp`, `src/device.c`, `startup.S`). Повторный ввод удаляет файл из набора. Команда `all` возвращает автоматическое сканирование. Для сборки приложения с тестовым `main()` выберите исходники **только нужной цели**.
3. **9/10/11**: настройте компилятор, дампы GCC, Embedded и карту памяти.
4. **12 → 2**: сохраните текущую конфигурацию в `.pgr/<target>.cfg`.
5. **1**: соберите цель. Результат `Release` будет в `C:/PGR/build/<имя_проекта>__Release/`, в том числе журнал `<имя_проекта>__Release.log`.

Названия целей допускают буквы латинского алфавита, цифры, `_` и `-`; `default` использует прежний каталог проекта без суффикса. Цели пока выбираются **по одной**, общего графа одновременной сборки нескольких программ нет.

### Embedded: отчёт по памяти

В меню **11 → 10** задайте адреса начала (десятичные или `0x...`) и размеры областей Flash/RAM **в байтах**, а в **11 → 1** включите отчёты. После сборки откройте `binary/memory.txt` через **11 → 8**. Адрес LMA учитывается при оценке Flash, VMA при оценке RAM, секция `.data` может занимать оба региона. Если размещённая секция пересекает границу заявленной памяти, анализ возвращает ошибку.

Это **проверка объявленных регионов, а не полная модель микроконтроллера**: неучтённые области, резервы bootloader, heap/stack, периферия и поведение startup-кода нуждаются в собственной проверке. Если размер региона равен нулю, проверка для него отключена. Образ `.bin` или `.hex` всё ещё не является доказательством работоспособности прошивки.

### Сборка и проверки

Сборка приложения (C++17):

```bat
g++ -std=c++17 -Wall -Wextra -Wpedantic main.cpp -o pgr_make.exe
pgr_make.exe .
```

Автоматические проверки:

```bat
python tests/test_regressions.py
python tests/test_incremental.py
python tests/test_analysis.py
python tests/test_embedded.py
```

`test_regressions.py` воспроизводит бывший дефект `.a`, изменение источника с восстановлением `mtime`, вредоносную строку в имени файла, зависимость `.S` от заголовка, неверный статус CLI, сохранение профиля и переполнение памяти. Тесты использованы в Linux/GCC; Windows/MSYS2 и реальный ARM toolchain требуется проверить на соответствующей машине.

### Оставшиеся ограничения

- Инкрементальность внешних библиотек гарантируется для обнаруженных файлов **в явных `-L`**, не для произвольно подгружаемых системных библиотек и сложных косвенных зависимостей GNU ld.
- Парсер `INCLUDE` в linker script упрощён; вложенные команды `INPUT/GROUP`, `SEARCH_DIR` и нестандартные конструкции сценариев ld не обрабатываются полностью.
- Изменения стандартных системных заголовков, не входящих в список `-MMD`, не учитываются по содержимому; изменение самого GCC учитывается.
- Сборка всё ещё последовательная; нет очереди параллельных заданий, отмены и тайм-аутов процессов. Нет автоматической генерации startup, таблицы векторов и конфигурации под конкретный MCU.
- `gcc_compilation_step_t` остаётся **описанием внутренних проходов**, а не отдельным API запуска фаз `cc1`/`cc1plus`.
- Профили хранятся в простом читаемом файле проекта без автоматического разрешения конфликтов параллельного редактирования. Прямой запуск Windows/MSYS2 пока не проходил CI.

## Этап 4. Анализ исполняемого файла и Embedded

**Реализовано:** после успешной четырёхэтапной сборки можно анализировать готовый ELF или PE/COFF, получать карту компоновки GNU ld, отчёты GNU Binutils, а также преобразовывать исполняемый файл в `.bin` и Intel HEX. Реализация размещена в `core/binary/binary.hpp` (header-only, `class binary_t`); `gcc_t` по-прежнему содержит отдельные методы `preprocessing()`, `compilation()`, `assembly()`, `linking()`.

### Запуск из циклического интерфейса

1. Откройте **`11. Executable / Embedded analysis`**.
2. Нажмите `1`, чтобы включить анализ готового ELF/PE; `2` для карты `.map`; `3` для образа `.bin`; `4` для Intel HEX `.hex`.
3. Вернитесь в главное меню и выполните `1. Build project (incremental)`.
4. Вернитесь в `11` → `8. Browse executable reports`, чтобы выбрать отчёт и просмотреть его первые 80 строк (максимум 12 КБ). Двоичные `.bin` не выводятся как текст, вместо этого отображается размер и путь.
5. После исправлений исходников повторите сборку. Неизменённые исходники, компоновка и отчёты пропускаются автоматически.

Все новые функции **выключены по умолчанию**, поэтому обычные проекты продолжат собираться без установленного `objdump` или `objcopy`.

| Отчёт или образ | Инструмент | Назначение |
|---|---|---|
| `binary/format.txt` | Сам PGR Make | Magic ELF/PE, путь, размер файла |
| `binary/file-headers.txt` | `objdump -f` | Архитектура и тип объектного файла |
| `binary/sections.txt` | `objdump -h` | Секции, VMA/LMA, размеры и флаги |
| `binary/symbols.txt` | `nm -n -C` | Символы в порядке адресов, деманглинг C++ |
| `binary/disassembly.txt` | `objdump -d -C` | Дизассемблирование исполняемых секций |
| `binary/size.txt` | `size -A` | Размеры по секциям |
| `binary/size-summary.txt` | `size -B` | Сводные `text`, `data`, `bss` |
| `binary/program-headers.txt` | `readelf -l` | Сегменты ELF и отображение секций |
| `binary/pe-headers.txt` | `objdump -p` | Заголовки PE/COFF (вместо readelf) |
| `linking/app.map` | GNU ld `-Wl,-Map=...` | Карта размещения секций и символов при компоновке |
| `binary/app.bin` | `objcopy -O binary` | Плоский бинарный образ |
| `binary/app.hex` | `objcopy -O ihex` | Intel HEX |

`app` в именах файлов является примером: используется основа имени текущего исполняемого файла, например `firmware.elf` → `firmware.map`, `firmware.bin`, `firmware.hex`. Формат файла определяется по magic, а не по расширению `.exe` или `.elf`.

### Подключение Embedded toolchain

Сначала необходимо установить **подходящий для целевого микроконтроллера кросс-компилятор GNU**. Наличие поддержки ARM в PGR Make не означает, что ARM GCC входит в этот архив.

Для типичного проекта Cortex-M можно выполнить следующие действия:

1. `11` → `5`: укажите префикс `arm-none-eabi-`. CLI согласованно установит `arm-none-eabi-gcc`, `arm-none-eabi-g++` и префиксы утилит Binutils (`objdump`, `nm`, `size`, `readelf`, `objcopy`). Путь к инструментам должен быть доступен через `PATH`; можно использовать префикс с полным путём к файлам.
2. `11` → `6`: добавьте флаги `-mcpu=cortex-m3` и `-mthumb` **каждый отдельной записью**. Флаги применяются ко всем этапам GCC, включая ассемблирование и компоновку.
3. `11` → `7`: выберите **настоящий linker script** для памяти вашей платы или МК, например `memory.ld`. Скрипт передаётся в GNU GCC драйвер через `-T`; его изменение отслеживается без повторной компиляции исходников.
4. `11` → `9`: при необходимости включите `-ffunction-sections`, `-fdata-sections` и `-Wl,--gc-sections`.
5. `9` → `3`: в настройках компоновщика задайте имя `firmware.elf` и дополнительные параметры, например `-nostdlib`, если исходники и окружение действительно позволяют собираться без стандартной библиотеки.
6. `11` → `1/2/3/4`: включите нужные отчёты, карту и форматы образов; выполните сборку `1`.

**Внимание:** PGR Make не создаёт автоматически таблицу векторов прерываний, startup-код, инициализацию `.data/.bss`, подходящий linker script, стандартные библиотеки или механизмы прошивки устройства. Эти компоненты зависят от конкретного МК и должны быть представлены в проекте. Создание `.bin`/`.hex` **не гарантирует**, что полученный образ можно загрузить и запустить на целевом устройстве.

Содержимое `size -A` / `size -B` и `objdump -h` характеризует секции и их адреса, но **не доказывает фактическое использование физической RAM/FLASH** без анализа linker script и адресов загрузки/исполнения; например, секция `.data` одновременно имеет место в RAM и загрузочное представление во FLASH.

### Инкрементальность этапа 4

- Меняется **только выбор отчётов Binutils** → GCC и ld не запускаются, пересоздаётся каталог `binary/`.
- Удалён отдельный отчёт из `binary/` → все указанные в манифесте результаты анализа восстанавливаются без повторной компиляции и компоновки.
- Меняется **параметр карты компоновки** → повторяется только `linking()`, а старая карта удаляется.
- Меняется **linker script** → повторяется только `linking()` и необходимый после неё анализ.
- Меняется **архитектурный флаг `-mcpu/-march/-mthumb`** → пересобираются соответствующие объектные файлы и выполняется компоновка.
- Меняется **префикс инструментов Binutils** → повторяется анализ, но не компиляция, если имена GCC-драйверов не изменились.
- При ошибке GNU Binutils этап сборки возвращает ненулевой код; кэш отчётов не обновляется.

Кэш постобработки хранится в `cache/binary.cmd`; манифест реальных отчётов хранится в `binary/manifest.txt`. `6. Clean` удаляет `binary/` и другие результаты, **не трогая `<проект>.log`**. Настройки сохраняются в `.pgr/<target>.cfg` по команде 12 → 2 и автоматически загружаются при выборе сохранённой цели; `default.cfg` загружается при запуске.

### Проверки Stage 4

```bat
python tests/test_embedded.py
python tests/test_analysis.py
python tests/test_incremental.py
```

`test_embedded.py` проверяет построение и запуск смешанного C/C++-проекта, полный комплект отчётов ELF, таблицу символов, карту с пробелами в пути, BIN/HEX, кэш анализа, удалённый отчёт, изменение target-флагов, изменение linker script, отключение карты, обработку недоступной Binutils-утилиты, magic распознавание ELF/PE и циклический CLI. Проверка PE включает распознавание magic и, при наличии `clang` + `lld-link`, создание реального PE32+ файла и извлечение его секций и заголовков с GNU Binutils. **Кросс-компиляция для MCU и запуск прошивки на микроконтроллере не проверялись**.

### Ограничения

- Для отчётов требуются GNU Binutils совместимой с файлом архитектуры: `objdump`, `nm`, `size`, `readelf` (только для ELF), `objcopy` (для BIN/HEX). Параметры Binutils могут отличаться для нестандартных портов.
- В Stage 5 запуск внешних инструментов выполняется **без оболочки** через `process_t` (POSIX `fork/execvp`, Windows `CreateProcessW`). Совместимость Windows/MSYS2 требует отдельной практической проверки; поддерживаются ограниченные перенаправления `>`, `2>`, `2>&1`.
- Для сжатых, stripped или нестандартных двоичных файлов отдельные отчёты могут быть ограничены возможностями установленных Binutils; PGR Make возвращает диагностический код при ошибке инструмента.
- Плоский `.bin` не является полной заменой ELF и может содержать большие незаполненные интервалы, если адреса загрузки секций существенно разнесены. Кроме того, Intel HEX ограничен адресами, которые способен представить выбранный `objcopy`: конвертация 64-битных PE-образов с высокими адресами может завершиться ошибкой.
- Сканер `project_t` обнаруживает `.c`, `.cpp`, `.cc`, `.cxx`, `.C`, а также `.s` и `.S`. Для `.S` выполняется препроцессирование с зависимостями, для `.s` непосредственное ассемблирование. Startup и linker script нужно предоставить в проекте.
- Поддержка реального Windows/MSYS2 и аппаратных кросс-компиляторов потребует проверки в соответствующей среде.

## Этап 3. Исследование GCC: frontend tree, GIMPLE, SSA, RTL

**Реализовано:** после включения режима исследования PGR Make сохраняет промежуточные представления GCC и отчёты **для каждого отдельного исходного файла**. Работа встроена в существующий `gcc_t::compilation()` и не нарушает разделение четырёх этапов `preprocessing()`, `compilation()`, `assembly()`, `linking()`.

### Использование через циклическое меню

1. Запустите `pgr_make.exe .` из корня проекта. В MSYS2 предварительно соберите саму программу по инструкции ниже.
2. Выберите **`10. GCC analysis and reports`** → `1. Mode` → `1. SELECTED` или `2. ALL`.
3. В меню `9. GCC build settings` при необходимости установите `-O2` для C и C++: тогда будут заметнее оптимизации.
4. Вернитесь в главное меню и выполните `1. Build project (incremental)`.
5. Выберите `10` → `4. Browse reports by source file`, укажите номер исходника и номер отчёта. Список длинных проходов листается через `n`/`p`; предпросмотр ограничен 80 строками/12 000 байтами.
6. Для полного текста откройте нужный файл непосредственно в редакторе. Пункт `6. Clean` удаляет также папку `analysis/`, но оставляет журнал `<проект>.log`.

| Режим | Аргументы GCC на этапе COMPILATION | Содержание |
|---|---|---|
| `OFF` (по умолчанию) | Дополнительных флагов нет | Обычная инкрементальная сборка; новые отчёты не создаются |
| `SELECTED` | `-fdump-tree-original`, `-fdump-tree-gimple`, `-fdump-tree-ssa`, `-fdump-tree-optimized`, `-fdump-rtl-expand`, `-fdump-rtl-final` | Шесть файлов с понятными именами для изучения основных переходов |
| `ALL` | `-fdump-tree-all -fdump-rtl-all -dumpdir ... -dumpbase ...` | Все доступные tree и RTL дампы с номерами/именами проходов для используемой версии GCC |

Флаги `-fopt-info-all=<файл>` и `-ftime-report` можно включать/выключать **отдельно**, когда выбран `SELECTED` или `ALL`. Время GCC записывается в `timing.txt`; технически файл содержит **stderr этапа компиляции**, поэтому в него могут попасть и предупреждения/ошибки. После завершения сообщения повторно передаются в обычный терминал и основной лог проекта, не теряя диагностику компилятора. `optimizations.txt` содержит отчёт об оптимизациях и пропущенных возможностях (в зависимости от уровня `-O`).

**Важно:** `-fdump-tree-original` показывает исходное дерево GCC до gimplification, но не является универсальным форматом экспорта всего представления GENERIC и не раскрывает отдельные токены лексера или полное AST. `gcc_compilation_step_t` по-прежнему описывает внутренние стадии, а не принудительно запускает отдельные проходы GCC.

### Структура результатов

```text
C:/PGR/build/ProjectName/
├── ProjectName.log                  общий журнал (остаётся после Clean)
├── preprocessing/                  .i / .ii
├── compilation/                    .s
├── assembly/                       .o
├── dependencies/                   .d
├── cache/                          .cmd
├── linking/                        app.exe
└── analysis/
    ├── main.cpp/
    │   ├── original.txt            исходное tree-представление
    │   ├── gimple.txt              GIMPLE
    │   ├── ssa.txt                 GIMPLE в форме SSA
    │   ├── optimized.txt           оптимизированное GIMPLE
    │   ├── rtl-expand.txt          начальное RTL
    │   ├── rtl-final.txt           заключительный RTL
    │   ├── optimizations.txt       решения оптимизатора (при включении)
    │   ├── timing.txt              stderr и время компиляции (при включении)
    │   ├── analysis.ok             список сгенерированных файлов для кэша
    │   └── full/                   нумерованные tree/RTL проходы в режиме ALL
    └── src/math.c/                 аналогичные отчёты для другого исходника
```

Структура внутри `analysis/` повторяет расположение исходника относительно корня проекта. При режиме `ALL` выборочные файлы с фиксированными именами не генерируются; вместо них создаются отдельные дампы `full/`. Старые отчёты конкретного исходника удаляются **перед его новой компиляцией**, чтобы не смешивать данные разных запусков.

### Совместимость с инкрементальной сборкой

- Параметры анализа входят в сигнатуру команды компиляции. Переключение режима или флагов отчётов вызывает необходимую пересборку, даже если исходный код не изменился.
- Повторный запуск с прежними настройками пропускает неизменённые файлы и не создаёт повторные дампы.
- Для каждого исходника записывается манифест `analysis.ok` со списком реально созданных файлов; удаление любого из них приводит к пересборке соответствующего исходника.
- При ошибке компиляции кэш успешного результата не обновляется. Перехваченные диагностические сообщения не теряются.
- Изменение только параметров компоновщика, как и на втором этапе, не вызывает повторную генерацию дампов.

### Программный интерфейс

Режим настраивается через объект `gcc_t::build_settings_t`:

```cpp
// Пример: включить исследование GIMPLE/SSA/RTL и отчёты GCC.
// config получен из gcc.get_build_settings().
config.analysis.mode = gcc_t::analysis_mode_t::SELECTED;
config.analysis.optimization_report = true;
config.analysis.time_report = true;
gcc.set_build_settings(config);
```

В `gcc.hpp` обновлены методы `compilation_command()`, `compilation()` и `run()`, добавлены генерация путей `analysis_path()`, контроль отчётов `analysis_current()` и сохранение манифеста. Остальные три функции этапов GCC по-прежнему самостоятельные. В `cli.hpp` добавлен пункт `10`, а команда `clean` очищает и `analysis/`.

### Ограничения

1. **Объём:** режим `ALL` может создавать сотни файлов и расходовать значительное дисковое пространство. Для обычной работы используйте `SELECTED`.
2. **Версии:** названия, количество проходов и содержимое дампов зависят от конкретной версии и сборки GCC; проверка выполнена с GCC 14.2.0. Windows/MSYS2 не проверялся в этой среде.
3. **Оптимизация:** при `-O0` GCC может не исполнять отдельные оптимизационные проходы. Если выбранный дамп отсутствует, программа добавляет файл с пояснением, чтобы отсутствие результата не приводило к бесконечной пересборке.
4. **Время:** отчёт GCC отражает внутреннее время компиляции и использование памяти компилятором; это не полный тайминг всех четырёх этапов PGR Make.
5. **Кэш:** в Stage 5 к временным меткам добавлены контрольные суммы зависимостей, объектных файлов и библиотек из явных `-L`; системные библиотеки, не найденные в явных каталогах, автоматически не хэшируются. Режим исследования можно сохранить в профиле.
6. **Запуск внешних процессов:** Stage 5 использует `process_t` с прямым запуском дочернего процесса и каналом вывода. Проверка Windows/MSYS2 пока необходима.

### Автоматическая проверка третьего этапа

```bat
python tests/test_analysis.py
python tests/test_incremental.py
```

`test_analysis.py` проверяет C/C++, имена путей с пробелами, выбранные и полные дампы, сохранение времени/оптимизаций, манифест, пропуск повторной сборки, изменение заголовков, изменение параметров анализа, восстановление после ошибки компиляции и запуск итогового файла. Тесты создают временный каталог и не требуют записи в `C:/PGR/build`.

## Этап 2. Зависимости и инкрементальная сборка

**Реализовано:** повторная сборка не запускает компилятор для неизменённых исходников. После успешной компиляции программа сохраняет список зависимостей и команды каждого исходного файла. При следующем запуске сравниваются время изменения зависимостей, наличие результатов и настройки сборки.

- GCC создаёт файлы зависимостей при **PREPROCESSING** с параметрами `-MMD -MP -MF <file>.d -MT pgr_dependencies`. `-MMD` отслеживает исходные файлы и пользовательские заголовки, но не системные заголовки.
- Список зависимостей извлекается из первой цели GNU Make (`.d`). Учитываются переносы строк и экранирование пробелов; вложенные `#include` тоже попадают в список.
- Для каждого исходника в `cache/` сохраняются команды препроцессирования, компиляции и ассемблирования. Если поменялись стандарт, оптимизация, предупреждения, отладочные/пользовательские флаги, компилятор или пути заголовков, пересобирается **только затронутый язык/исходник**.
- При пропуске файла **не запускается ни один из трёх этапов**. Четыре отдельные функции `preprocessing()`, `compilation()`, `assembly()` и `linking()` в `gcc_t` сохранены.
- Компоновка выполняется только при обновлении объектных файлов, изменении набора исходников, имени `.exe`, библиотеках/линкерных флагах либо отсутствии/устаревании исполняемого файла.
- После успешной сборки сохраняется сигнатура команды компоновки; при ошибке компиляции/линковки кэш успешного результата **не обновляется**.
- В терминале и журнале показываются `[BUILD] CHANGED`, `[SKIP] UP-TO-DATE`, `[LINK] UP-TO-DATE` и `[SUMMARY] Rebuilt / Skipped / Linking`.
- Пункт меню `6. Clean build artifacts` удаляет также `dependencies/` и `cache/`, сохраняя `<project>.log`. Следующая сборка после очистки будет полной.

### Каталоги результатов

Для проекта `demo` по умолчанию используется `C:/PGR/build/demo/`:

```text
C:/PGR/build/demo/
├── demo.log                 журнал (не удаляется командой Clean)
├── preprocessing/           .c.i, .cpp.ii
├── compilation/             .c.s, .cpp.s
├── assembly/                .c.o, .cpp.o
├── dependencies/            .c.d, .cpp.d
├── cache/                   .c.cmd, .cpp.cmd, linking.cmd
└── linking/                 app.exe
```

Относительные пути исходников сохраняются во всех каталогах, чтобы, например, `src/main.cpp` и `tests/main.cpp` не конфликтовали по имени артефакта. Кэш сохраняется между запусками приложения.

### Что пересобирается

| Событие | Исходные файлы | Компоновка |
|---|---|---|
| Первое построение | Все | Да |
| Повторный запуск без изменений | Ни один | Нет |
| Изменён `.cpp` | Только этот `.cpp` | Да |
| Изменён `.h/.hpp` | Только исходники, включающие заголовок | Да |
| Изменены опции C, а опции C++ нет | Только C-исходники | Да |
| Изменены только опции линковщика | Ни один | Да |
| Добавлен/удалён исходный файл | Новый файл или ни одного при удалении | Да |
| Удалён промежуточный файл | Соответствующий исходник | Да |
| Выполнен Clean | Все при следующей сборке | Да |

### Ограничения

1. Актуальность определяют времена изменения файлов и сигнатуры команд. Изменения с искусственно сохранёнными метками времени не обнаруживаются; для таких случаев используйте Clean.
2. В этой версии `-MMD` не отслеживает изменения **системных** заголовков. Для изменения toolchain или системных библиотек используйте Clean.
3. Появление ранее отсутствовавшего необязательного заголовка, проверяемого через `__has_include`, не всегда отражается в прежнем `.d`; для таких изменений используйте Clean.
4. Файлы кэша описывают успешно выполненные команды, но не криптографический хеш содержимого. Внешнее ручное изменение объектов без изменения меток времени не обнаруживается.
5. В этой версии выполняется последовательная сборка. Параллельная сборка и постоянное сохранение настроек CLI не добавлены.

## Этап 1. Настройки компиляции

Через пункт **9. GCC build settings** доступны:

- независимые стандарты C (C99/C11/C17/C23) и C++ (C++11/14/17/20/23);
- оптимизации `-O0`, `-O1`, `-O2`, `-O3`, `-Os`, `-Og`;
- предупреждения `-Wall`, `-Wextra`, `-Wpedantic`, переключатель `-Werror`;
- отладочная информация `-g`, `-g3`;
- пользовательские флаги GCC, каталоги заголовков `-I`, библиотеки `-l`, каталоги `-L`, параметры компоновщика;
- выбор имён компиляторов (`gcc`, `g++`) и исполняемого файла.

Параметры CLI сохраняются **только в текущем сеансе**, но идентичный набор параметров после перезапуска позволяет использовать созданный ранее кэш. Режим C23 передаётся как `-std=c2x` для совместимости с GCC 13.

## Сборка и запуск

В Windows CMD или терминале MSYS2 UCRT64, из корня исходного проекта:

```bat

pgr_make.exe .
```

Главное меню работает в цикле:

| Пункт | Назначение |
|---|---|
| `1` / `build` | Инкрементальная сборка выбранного проекта |
| `2` / `project` | Выбор проекта |
| `3` / `info` | Сведения о проекте и настройках GCC |
| `4` / `sources` | Список исходных файлов |
| `5` / `log` | Последние 40 строк журнала GCC |

| `0` / `exit` / `quit` | Выход |

### Сборка самого PaperGooseRus_Make

В исходном проекте есть `test/main.cpp` со второй точкой входа. Для самосборки выберите в меню `7` и исключите `test`. Если GTK не установлен, исключите также `gui`; иначе для GTK необходимо вручную указать соответствующие компиляторные и линкерные флаги. Затем дважды выберите пункт `1`.

В первый раз появятся этапы GCC и сообщение вида:

```text
[SUMMARY] Rebuilt: 2 | Skipped: 0 | Linking: YES
```

Во второй раз:

```text
[SKIP] UP-TO-DATE -> "core/loger/loger.cpp"
[SKIP] UP-TO-DATE -> "main.cpp"
[LINK] UP-TO-DATE -> "C:/PGR/build/PaperGooseRus_Make/linking/app.exe"
[SUMMARY] Rebuilt: 0 | Skipped: 2 | Linking: NO
```

На Windows каталог сборки будет расположен по указанному абсолютному пути. Журнал сохранится в `C:/PGR/build/PaperGooseRus_Make/PaperGooseRus_Make.log`.

## Архитектура

| Файл | Ответственность |
|---|---|
| `main.cpp` | Создание CLI, передача общих настроек и подключение логгера |

## Проверка

Для самостоятельной проверки при установленном Python 3 и GCC:


Скрипт во временном каталоге собирает смешанный проект C/C++ и проверяет первые/повторные сборки, изменение заголовка с пробелом в имени и вложенной зависимости, изменение опций C/компоновщика, добавление/удаление исходника, удаление промежуточного файла и восстановление после ошибки компиляции. ## Stage 6 (UI): графический интерфейс GTK4 в одном заголовочном файле

Графический интерфейс реализован **только в `gui/gtk_app.hpp`**. Файл `gui/gtk_app.cpp`
удалён. Исходные модули `project_t`, `gcc_t`, `binary_t`, `config_t`, `loger_t`
продолжают выполнять сборку и анализ без зависимости от GTK4.

### Возможности

- **Проект**: выбор каталога, общий корень результатов, имя цели/профиля,
  открытие каталога сборки, сохранение/загрузка `.pgr/<цель>.cfg`.
- **Исходники**: сканирование `.c/.cpp/.s/.S`, исключение каталогов, выбор файлов
  для конкретной цели; изменённый набор применяется кнопкой или перед сборкой.
- **GCC**: независимые стандарты, оптимизации, предупреждения, отладочные символы,
  `-Werror` и дополнительные флаги для C/C++; GCC/G++, библиотеки, пути и компоновщик.
- **Исследование GCC**: `OFF`, `SELECTED`, `ALL`, отчёты оптимизации и времени.
- **Embedded**: настройки GNU Binutils, BIN/HEX, linker map, флаги процессора,
  linker script, области Flash/RAM, просмотр отчётов `binary/`.
- **Журнал**: просмотр `<build>/<project>/<project>.log` с ограничением объёма
  256 КиБ; обновление во время сборки и отображение её результата.
- **Фоновая сборка**: GTK4 не блокируется на вызовах GCC. Закрытие окна и
  очистка результатов блокируются, пока выполняется сборка.

**Сохранение настроек** выполняется кнопкой «Сохранить профиль»; изменение полей
перед сборкой применяется к текущему запуску. В списочных полях разделителем
служит `;`, поэтому путь, содержащий точку с запятой, использовать нельзя.
Это ограничение именно текстовых полей GUI, не `project_t` или GCC.

### Windows/MSYS2 UCRT64

Установить необходимые пакеты в терминале **MSYS2 UCRT64**:

```bash
pacman -S --needed mingw-w64-ucrt-x86_64-gcc mingw-w64-ucrt-x86_64-gtk4 mingw-w64-ucrt-x86_64-pkgconf
```

Из корня проекта:

```bash
./build_gui.sh
./build/pgr_gui .
```

Из CMD с настроенным `PATH` на `C:\msys64\ucrt64\bin`:

```bat
build_gui.cmd
build\pgr_gui.exe .
```

На Windows скрипт `.cmd` создаёт `build\pgr_gui.exe`, а `.sh` — `build/pgr_gui`.
Используется GTK4 из выбранного toolchain; не следует смешивать UCRT64 и MINGW64.

Ручная команда:

```bash
g++ -std=c++17 -Wall -Wextra -Wpedantic -pthread -DPGR_WITH_GTK4 \
    $(pkg-config --cflags gtk4) main.cpp -o pgr_gui.exe \
    $(pkg-config --libs gtk4)
```

### Консольный интерфейс сохранён

```bash
g++ -std=c++17 -Wall -Wextra -Wpedantic main.cpp -o pgr_cli.exe
./pgr_cli.exe .
```

Если программа скомпилирована с `-DPGR_WITH_GTK4`, CLI доступен через
`pgr_gui.exe --cli [путь_к_проекту]`.

### Ограничения текущего GTK4 UI

- Нет отмены уже запущенного GCC или параллельной сборки.
- Журнал и отчёты показываются как текст; графическое сравнение GIMPLE/RTL не реализовано.

## Исправление совместимости с Windows SDK и GTK4

- `warning_t::STRICT` переименован в `warning_t::STRICT_WARNINGS`: устранён конфликт с макросом `STRICT` в `windows.h` (числовое значение режима предупреждений не менялось, сохранённые профили совместимы).
- `NOMINMAX` определяется только при отсутствии такого определения в системных заголовках.
- GTK CSS загружается через `gtk_css_provider_load_from_string()` с GTK 4.12, на старых версиях остаётся `gtk_css_provider_load_from_data()`.
- `tests/test_gtk_ui.py` дополнительно компилирует проект с `-DSTRICT=1 -DNOMINMAX=1` для обнаружения регрессии.

Для проверки в **MSYS2 UCRT64** запустите `build_gui.cmd` из `cmd.exe` с добавленным `C:\msys64\ucrt64\bin` в `PATH` или `./build_gui.sh` в терминале UCRT64. В текущей тестовой среде Windows SDK и GTK4 не установлены, поэтому окончательное подтверждение реальной Windows/GTK4 сборки требуется выполнить локально.


## GTK4: системная тема и самосборка без устаревшего `.cpp`

Интерфейс использует **только стандартные виджеты GTK4**. Собственный CSS, цветовые
переопределения, классы оформления и принудительный моноширинный шрифт удалены.
GTK4 самостоятельно выбирает оформление из темы, настроенной в системе.

### Исправление ошибки `gtk/gtk.h: No such file or directory`

Эта ошибка в ранее опубликованном журнале возникла **при сборке PGR Make из самого
GUI**, а не в команде `build_gui.cmd`. Причина: старый файл `gui/gtk_app.cpp`
оставался в локальном каталоге и попадал в список компилируемых исходников.
В текущем проекте GTK-интерфейс реализован **только в `gui/gtk_app.hpp`**.

Если ранее распаковывали архив поверх существующего каталога, вручную удалите
устаревший `gui/gtk_app.cpp`:

```bat
del gui\gtk_app.cpp
```

Это однократная очистка **только указанного устаревшего файла**. Новая GTK-версия
дополнительно исключает его из сканирования собственного проекта, если файл
остался на диске, а при автоматической самосборке исключает `test/` со вторым
`main.cpp`. Для чужих проектов правила сканирования не меняются.

### Разница между сборкой CLI и GTK4

**Консольная версия** PGR Make не требует GTK4 и может собираться без дополнительных
заголовков и библиотек. Чтобы выполнить **самосборку графической версии** через
GUI, откройте исходники PGR Make в разделе «Проект» и нажмите
**«Настроить самосборку GTK4»**. Эта кнопка:

1. Запрашивает `--cflags` и `--libs` с помощью `pkg-config gtk4` (без запуска оболочки).
2. Добавляет `-DPGR_WITH_GTK4`, каталоги заголовков, библиотеки и параметры компоновки.
3. Переключает сборку на отдельную цель `GTK4` и имя `pgr_gui.exe` под Windows.
4. Исключает устаревший CPP и тестовый `main.cpp` в режиме автосканирования.

После этого нажмите «Сохранить профиль», затем «Собрать». Результат появится в
`C:/PGR/build/PaperGooseRus_Make__GTK4/linking/pgr_gui.exe` при настройках по
умолчанию. Для обычной консольной сборки используйте профиль `default`.

Для внешнего проекта флаги GTK4 не добавляются автоматически: это управляемое
действие только для сборки самого PGR Make. Чтобы `pkg-config` обнаружил GTK4
под Windows, выполните `build_gui.cmd` и запустите приложение в среде с каталогом
`C:\msys64\ucrt64\bin` в переменной `PATH`.

Примечание по тестированию: тесты CLI и предыдущих этапов выполняются без GTK4.
Полная проверка GUI требует установленного GTK4 SDK и выполняется через
`python tests/test_gtk_ui.py` в MSYS2 UCRT64.
